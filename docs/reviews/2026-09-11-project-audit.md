**Подтверждённые проблемы и приоритеты**

**1. P1 — не терять результат задачи при отказе и проверять завершение одним циклом.**

`_can_retry_incomplete_task()` сразу возвращает false для завершённой секции. Проверка отсутствия коммита и новых dirty-файлов происходит позже. Поэтому задача с закрытым чек-листом не получает corrective retry для этих двух ошибок. Контекстный менеджер затем безусловно удаляет task-worktree.

Воспроизведение `dirty_completion`: агент закрыл пункты, закоммитил план и оставил полезный `valuable-result.txt` неотслеживаемым. Получены **один вызов агента**, исключение и удалённый worktree; файла нет в основной копии. Незакоммиченный файл исчезает. Коммиты могут какое-то время оставаться недостижимыми объектами Git, но штатного пути восстановления результата нет.

Это соответствует последнему обсуждению. В доступном [логе 25 августа](</Users/alexeyromanov/Downloads/progress 2/progress-2026-08-25-ssot-pipeline.txt:67>) видны удаление worktree и `completed without creating a commit`. Сообщение о новых файлах в задаче domain-extraction есть в предыдущей задаче пользователя; отдельный полный лог этого случая здесь не проверялся.

Изменение: единая проверка завершения возвращает конкретные нарушения — незавершённый пункт, отсутствие коммита, новые незакоммиченные файлы, изменение требований. Исправимые нарушения получают ограниченную попытку в том же worktree. При окончательном отказе сохранить коммиты и незакоммиченные артефакты в пакет восстановления, затем удалить временную копию. Не коммитить и не удалять неизвестные файлы автоматически ради формального успеха. Ошибка должна указывать на сохранённый результат.

**2. P1 — требования должны оставаться неизменными, а отметка агента не должна заменять проверку.**

Воспроизведение `deleted_requirement`: из двух обязательных пунктов агент отметил первый, удалил второй и закоммитил только план. Runner принял задачу. Текущая секция проверяется по оставшимся checkbox, а сохранность её исходных требований не проверяется. Для последующих секций сравниваются checkbox, но не вся содержательная часть; предыдущие секции этим методом не защищены.

Ближайшее изменение: зафиксировать исходный документ и разрешить только заранее определённые изменения статуса выбранных пунктов либо добавление точного маркера для prose-задачи. Защитить формулировки, состав пунктов и остальные секции. Аналогичные проверки нужны в synthesis и finalize: нынешняя защита OpenSpec-контекста применяется только в task-фазе.

Для аналитики допустимы проверки схем, расчётов, источников и артефактов. Агент сообщает, что готово, runner принимает решение о завершении и обновлении статуса. Переход можно сделать совместимым, явно различая проверку runner и сообщение агента.

**3. P1 — synthesis и finalize должны соблюдать тот же контракт результата, что и задачи.**

Воспроизведение `dirty_synthesis`: synthesis исправил tracked-файл, не закоммитил его и вернул `fixed`. Следующее ревью проверило snapshot и не нашло замечаний. Finalize вернул успех. Весь запуск завершился успешно с ` M result.txt`, хотя **allow_dirty=False**.

Причина: после synthesis отсутствует обязательная проверка завершения изменяющей фазы. Finalize принимает грязное состояние как своё исходное и смотрит только на появление новых путей. Проверка множеств путей также не обнаруживает изменение содержимого файла, который уже был dirty.

Воспроизведение `finalize_mutation`: после чистого ревью finalizer изменил код, создал коммит и сообщил `FINALIZE_DONE`. Запуск успешен, хотя последний коммит не проходил ревью. Сам prompt допускает «reasonable fixes», поэтому это не только сценарий заведомо неверного ответа агента.

Изменение: применять к synthesis тот же механизм изолированного кандидата, проверки и promotion. Finalize сделать проверкой зафиксированного результата. Если нужна правка, она проходит через ремонт и повторную проверку затронутого результата, затем finalize повторяется. Успех должен ссылаться на проверенное содержимое и выполненные проверки. Перенос обычного плана в completed обрабатывать как отдельное проверяемое служебное изменение.

**4. P2 — checkpoint должен учитывать правила проверки и сохранять незавершённое ревью.**

Воспроизведение `changed_review_policy`: после успешного ревью изменён фактический review prompt, затем выполнен обычный повторный запуск. Новый reviewer не вызван: **ноль новых review batch**. Checkpoint учитывает identity, base, HEAD и tree, но не условия, при которых результат был проверен. Явный `--review` принудительно проверяет заново; проблема относится к автоматическому возобновлению обычного запуска.

Кроме того, checkpoint сохраняет завершённые фазы. Решения по находкам, бюджет ремонтов и результаты отдельных ревьюеров остаются в памяти. После прерывания внутри ревью процесс начинает его заново. Статистика записывается в файл при старте и завершении, а не после каждого вызова; следующий запуск использует те же имена файлов. Это мешает анализировать накопленные затраты и восстановление после аварии.

Изменение: расширить существующий checkpoint небольшим manifest запуска. Сохранять run_id, базу, идентичность задачи, fingerprint фактических правил/промптов/валидаторов, состояние кандидата, решения ревью и потраченный бюджет. Версии runner, GigaCode и выбранную модель записывать для воспроизводимости. Сохранять состояние и статистику после каждого завершённого вызова. Продолжать тот же незавершённый run; отдельным новым запуском считать сознательное изменение задачи или условий. Для двух процессов, пишущих в одну execution-ветку, нужен общий lock.

**5. P2 — останавливать повторение без прогресса и измерять пользу ревью.**

Воспроизведение `confirmed_stall`: на неизменном репозитории повторяется одна и та же находка, synthesis каждый раз возвращает `confirmed`. При бюджете два ремонта runner делает три прохода ревью и два synthesis, затем исчерпывает бюджет. Текущий default — десять ремонтов. Цикл ограничен, но отсутствие прогресса не меняет поведение.

Не требуется немедленно отвергать любой `confirmed`: независимая перепроверка может опровергнуть находку. После такой перепроверки повторение того же дефекта на том же состоянии должно давать содержательный unresolved/stalled результат, а не новый идентичный ремонт. `fixed` без изменения результата также нуждается в проверке. Идентификаторы F001 назначаются заново внутри batch; для продолжения нужны сохранённые записи находок и их связь с проверяемым состоянием, а не только номер или дословное совпадение evidence.

Это суммарные входы внутренних обращений; это не размер одного контекста и не оценка денежной стоимости. Прогон относится к версии с нарезкой, до её удаления, поэтому эти цифры нельзя приписывать текущей версии без измерения.

Сохранить выбранное правило: первый проход — пять специалистов; дальше quality и implementation плюс специалисты из актуальных исправлений. Сокращать первый набор стоит лишь после сравнения на одинаковых задачах: число подтверждённых уникальных дефектов, ложных находок, повторных открытий, успешных завершений и затраты по фазам. Первым шагом выгоднее устранить лишние циклы. Классификацию постоянных и временных ошибок тоже следует использовать при решении о retry: сейчас общий executor повторяет практически любой отказ, кроме специальных остановок.

**6. P2 — явно описать состав результата и окружение изолированной задачи.**

Сохранённый base SHA решил проблему неправильной исходной ветки. Он не определяет, какие незакоммиченные файлы принадлежат результату. Review snapshot по-прежнему строится из всего tracked и non-ignored untracked состояния. Поэтому при allow-dirty ревью захватывает и сохранённые посторонние изменения. Отсюда исторические вопросы о 97 файлах. Один diff-файл отражает выбранную область сравнения; его формат не исправляет выбор области.

Рекомендация: сохранить накопленную branch-base семантику и явно строить проверяемый кандидат из результата ветки, task-коммитов и принятых dirty-файлов. Остальные пользовательские файлы должны сохраняться как контекст/исходные данные, а не автоматически становиться объектом исправления. Runner уже вычисляет touched/adopted paths при promotion — сохранять эти данные полезнее, чем определять принадлежность ещё одним агентом.

Отдельно важна воспроизводимость: задача работает в snapshot с пользовательскими dirty-входами, но в коммит попадает только принятая часть. Проверять нужно и переносимый результат с явно объявленными входами. Для аналитических задач это могут быть внешние данные; требование не означает обязательного помещения всех данных в Git.

Перенос путей сейчас применяется к полям PromptContext, а не к абсолютным путям внутри текста плана или команд. Игнорируемые локальные настройки и промежуточные артефакты тоже не переносятся обычным Git snapshot. Это требует интеграционных проверок на реальном GigaCode. Лог 25 августа показывает уход к исходному проекту, но не доказывает, какой именно путь или настройка его вызвали. Нужен явный контракт execution_root, доступных входов и допустимых выходов, а не слепая замена всех абсолютных путей в тексте.

Не возвращаться к усложнению пакетов на основании предположения об API 400. В доступном успешном логе все пять специалистов получили tool-result до **295 521 символа** и завершились без API-ошибки. Это опровергает объяснение через универсальный маленький порог, но не исключает зависимость сбоя от контекста или backend. При следующем таком инциденте фиксировать версию CLI, реальный model id, fingerprint prompt, размер и состав контекста, стадию ошибки и доступные сведения backend. Изменять по одному фактору и сохранять минимальный воспроизводимый случай.

Упростить prompt-контракты после введения проверок в коде. Сейчас к шаблонам дописываются исключения вида «поздняя инструкция отменяет предыдущую», а память решений, guards и форматные требования накладываются слоями. Требования, проверяемые программно, должны жить в runner; prompt должен объяснять работу и ожидаемый ответ. Это не требует немедленной смены формата протокола на JSON или зависимости от новой API-возможности.

В runtime около 8,9 тысячи строк Python, включая промпты и HTML dashboard; в тестах около 8,1 тысячи. Проблема не в количестве строк. После общих инвариантов стоит объединить почти одинаковые single/parallel review loops и вынести правила переходов из Runner, используя уже существующий Git-слой. Универсальный framework агентов, новый язык, серверный UI и миграция на другой provider сейчас не устранят подтверждённые дефекты.

**Предлагаемый порядок работ**

| Очередь | Ограниченная поставка | Критерий готовности |
|---|---|---|
| 1 | Единая проверка завершения task, corrective retry для missing commit/dirty output, пакет восстановления; защита содержания плана | Полезный результат не исчезает при отказе; удаление требования отклоняется; основной checkout сохраняется при неуспешной попытке. |
| 2 | Такой же контракт для synthesis; независимые проверки runner; finalize проверяет зафиксированный результат | Сценарии dirty_synthesis и finalize_mutation больше не завершаются ложным успехом; после правки проверяется актуальный результат. |
| 3 | Manifest/checkpoint с правилами проверки, состоянием ревью и бюджетом; сохранение статистики после вызовов; no-progress detection | Изменившиеся правила не используют старый успех; прерванное ревью продолжается; неизменный дефект не расходует весь бюджет. |
| 4 | Явные входы/выходы и область результата; набор воспроизводимых интеграционных сценариев; синхронизация документации | Чистый проект, dirty-входы, OpenSpec, аналитика, постоянная API-ошибка и прерывание покрыты повторяемыми проверками; документация описывает проверенные гарантии. |

Первые две поставки дают основную пользу. Третья устраняет повторную оплату уже выполненной работы временем и вызовами. Четвёртая позволит менять промпты и состав ревью по данным.

Штатные тесты полезны: они проверяют parser, протокол, subprocess и настоящие Git-операции. Шесть дополнительных сценариев показывают пробелы именно между этими частями. Их следует превратить в проверки ожидаемого поведения при реализации исправлений. Далее нужен небольшой корпус обезличенных реальных отказов и воспроизведение stream-json, а не только увеличение числа assertions на текст prompt. Автоматический запуск suite и проверку установки wheel имеет смысл добавить в CI; workflow CI в текущем репозитории отсутствует.
